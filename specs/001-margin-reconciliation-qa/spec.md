# Feature Specification: Daily Margin & Growth Copilot

**Feature Branch**: `main` (no per-feature branch — single-feature take-home prototype)

**Created**: 2026-08-28 · **Updated**: 2026-08-28 (added promo-ROI scope, Product A / KR3)

**Status**: Draft

**Input**: User description: "Daily close and margin/growth copilot for an
independent restaurant/bar: ingest delivery-platform, POS, supplier-cost, and
promotion-spend exports; deterministically reconcile margin and flag
underperforming promotions; let the owner ask natural-language questions
about the day/week with typed-tool-backed answers, provenance, refusal on
ambiguous/unanswerable questions, and visible cost/token instrumentation."
(derived from `docs/product-strategy.md` — OKR Objective, KR1–KR4, and the
Product A decision — and `CLAUDE.md`, already committed to this repo.)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - See today's reconciled margin (Priority: P1)

The owner opens the app after uploading (or with pre-loaded) today's
delivery-platform export, POS export, and supplier cost sheet, and sees a
reconciled margin figure for the day — with every number traceable to its
source file, rows, and period.

**Why this priority**: This is the entire reason the product exists — the
owner currently discovers margin slippage at month-end. Nothing else matters
if this number isn't right.

**Independent Test**: Load a day's source files (including the deliberate
mess — duplicate order, refund, missing day, inconsistent date format) and
confirm the displayed margin matches an independently computed reference
value, with visible provenance. No natural-language question required.

**Acceptance Scenarios**:

1. **Given** a day's delivery, POS, and cost-sheet files with no anomalies,
   **When** the owner views the day, **Then** the system shows a margin
   figure that matches manual computation exactly, with source citations.
2. **Given** a day's files containing a duplicate order and a refund,
   **When** reconciliation runs, **Then** the duplicate is not double-counted
   and the refund is netted out, with the adjustment visible in the
   provenance trail.
3. **Given** a day with a missing file (e.g., no delivery-platform export),
   **When** the owner views that day, **Then** the system states plainly
   what's missing rather than silently omitting it from the margin figure.

---

### User Story 2 - Ask natural-language questions about the day/week (Priority: P2)

The owner asks questions in plain language ("how did we do today?", "why did
margin drop this week compared to last?") and gets an answer grounded in the
reconciled data, not a model-generated estimate.

**Why this priority**: This is what makes the tool usable day-to-day instead
of requiring the owner to read a table — but it depends entirely on User
Story 1 already being correct.

**Independent Test**: With reconciled data already available, ask the ~15–20
accuracy-evaluation questions with independently known correct answers and
confirm the answers match, each with provenance and a plain-language
explanation.

**Acceptance Scenarios**:

1. **Given** reconciled data for the current week, **When** the owner asks
   "how was this week compared to last week?", **Then** the system returns
   the week-over-week delta with the specific dates it used.
2. **Given** the same underlying question asked in three different
   phrasings, **When** each is submitted, **Then** all three answers agree.
3. **Given** a question whose answer requires a computation, **When** it is
   answered, **Then** the number shown was produced by the reconciliation
   engine, not generated by the model narrating the question.

---

### User Story 3 - Refuse or clarify instead of guessing (Priority: P3)

When a question is ambiguous (e.g., "how was the weekend" — does it include
Friday?) or cannot be answered from the available data, the system asks a
clarifying question or explicitly refuses, rather than producing a plausible
but unfounded answer.

**Why this priority**: This is the direct demonstration of the project's
central architectural bet (Constitution Principle II) and the hardest thing
to get an LLM-backed system to do reliably — but it only matters once Story 1
and 2 already work, since a system with no correct answers can't be usefully
evaluated for refusing incorrectly.

**Independent Test**: Ask the ~5 refusal-evaluation questions that cannot be
answered from the ingested data (e.g., asking about a supplier not in the
cost sheet) and confirm each produces a refusal or clarifying question, never
a fabricated number.

**Acceptance Scenarios**:

1. **Given** a question referencing data not present in any source file,
   **When** it is asked, **Then** the system states it cannot answer and
   says what's missing, rather than estimating.
2. **Given** an ambiguous date range in a question, **When** it is asked,
   **Then** the system either asks which range was meant or explicitly
   states the assumption it made before answering.
3. **Given** a question that would require more tool calls than the
   configured cap, **When** it is asked, **Then** the system stops and
   reports that it could not complete the request, rather than returning a
   partial, unlabeled answer.

---

### User Story 4 - Flag underperforming promotions (Priority: P4)

The owner asks about (or is shown) promotions or sponsored placements running
below their cost in incremental revenue, so spend can be redirected toward
what's actually working — the revenue-growth lever (KR3), built on the same
reconciled, provenanced pipeline as Stories 1–3.

**Why this priority**: This is the growth-side half of the Objective
("increase revenue without eroding margin") — it depends on the same
deterministic core and refusal discipline already proven by Stories 1–3, so
it's built last, once that core is trustworthy, not in parallel with it.

**Independent Test**: Load test data including at least one promotion
whose spend exceeds the incremental revenue it drove, and confirm the system
flags it correctly with the computed ROI and provenance — independent of any
margin question being asked.

**Acceptance Scenarios**:

1. **Given** a promotion whose incremental revenue is below its cost,
   **When** the owner asks about it, **Then** the system reports the
   negative ROI with the specific orders and spend it was computed from.
2. **Given** a promotion whose incremental revenue exceeds its cost,
   **When** evaluated, **Then** the system does not flag it, and states its
   positive ROI if asked.
3. **Given** insufficient data to attribute incremental revenue to a
   specific promotion, **When** asked about it, **Then** the system refuses
   to assert an ROI figure rather than guessing — the same Principle II
   discipline as Stories 1–3, applied to the growth side.

### Edge Cases

- A day's data arrives with an inconsistent date format between the
  delivery-platform export and the POS export.
- The same order appears twice in the delivery-platform export (duplicate).
- A refund is issued for an order from a prior period.
- A day is missing entirely from one of the three sources.
- A question spans a period that crosses a missing day.
- A tool call exceeds its timeout.
- The model attempts more tool calls than the configured per-interaction cap.
- A promotion's spend record exists but its attributed incremental orders are missing or incomplete.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST ingest delivery-platform export, POS export, and
  supplier cost-sheet files for a given day or period.
- **FR-002**: System MUST reconcile ingested records into a single margin
  computation per day, correctly handling duplicate entries, refunds, and
  inconsistent date formats without silent data loss.
- **FR-003**: System MUST compute week-over-week margin deltas and flag
  anomalies exceeding a defined threshold.
- **FR-004**: Users MUST be able to ask natural-language questions about a
  given day or week and receive an answer grounded in the reconciled data.
- **FR-005**: Every answer presenting a number MUST include its provenance
  (source file, rows, period).
- **FR-006**: System MUST evaluate each question for answerability and
  ambiguity before answering; ambiguous questions MUST prompt a clarifying
  question, or proceed while explicitly stating the assumption taken.
- **FR-007**: System MUST refuse to answer, rather than estimate, when
  required data is missing or the question cannot be answered from available
  data.
- **FR-008**: System MUST record, per interaction, input/output tokens,
  model used, estimated cost, latency, and whether a refusal or clarifying
  question fired.
- **FR-009**: Users MUST be able to see a running total of interaction cost.
- **FR-010**: System MUST cap tool-call iterations per interaction and apply
  a timeout to every tool call.
- **FR-011**: System MUST ingest promotion/sponsored-placement spend records
  alongside delivery-platform, POS, and cost-sheet data.
- **FR-012**: System MUST compute an incremental-revenue-to-spend ratio per
  promotion and flag any promotion where cost exceeds incremental revenue.
- **FR-013**: When a promotion's incremental revenue cannot be attributed
  from available data, the system MUST refuse to assert an ROI figure for
  it, per the same discipline as FR-007.

### Key Entities

- **Daily Reconciliation**: date, gross sales by source, commissions,
  refunds, input costs, computed margin, discrepancy flags, references to
  the source file rows it was computed from.
- **Question Interaction**: question text, resolved period, answer text,
  provenance references, tokens/cost/latency, whether a refusal or
  clarification fired.
- **Source Data File**: delivery-platform export, POS export, supplier
  cost sheet, promotion/ad-spend export — each carrying known, deliberate
  irregularities used to prove the reconciliation logic.
- **Promotion / Ad Spend Record**: platform, campaign identifier, spend
  amount, period, attributed incremental orders and revenue, computed ROI,
  references to the source rows it was computed from.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: On a set of ~15–20 accuracy questions with independently
  computed correct answers, the system answers correctly at a rate that is
  measured and reported, including any failures — no target is asserted in
  advance of measurement, per Constitution Principle V.
- **SC-002**: On ~5 questions each asked in 3 phrasings, the rate at which
  all 3 phrasings agree is measured and reported, including failures.
- **SC-003**: On ~5 questions that cannot be answered from the available data,
  the system responds with a refusal or clarifying question — not a
  fabricated answer — and this rate is measured and reported.
- **SC-004**: Every number shown to the user carries a visible, checkable
  source citation, with zero exceptions.
- **SC-005**: Per-interaction cost, token usage, and latency are visible to
  the user for 100% of interactions, from the first interaction onward.
- **SC-006**: On a set of promotions including at least one
  negative-ROI case, the system correctly flags it end-to-end (ingestion
  through natural-language answer) with provenance — the KR3 growth-lever
  proof point.

## Assumptions

- Single restaurant/bar, single currency, single time zone — no multi-tenant
  or multi-location support in this build (explicit non-goal).
- "Week" defaults to a trailing 7-day window ending on the query date unless
  the question specifies otherwise; genuine ambiguity here is handled by the
  ambiguity gate (FR-006), not pre-decided in this spec.
- The anomaly-flagging threshold (FR-003) is a configurable percentage
  deviation from a trailing average, tuned during implementation against the
  test data rather than fixed here.
- Synthetic test data (not live integrations) stands in for real delivery-platform
  and POS exports; connecting to real platform APIs is out of scope.
- No specific numeric targets are set in advance for SC-001–SC-003 — per the
  brief and Constitution Principle V, these are measured honestly and
  reported including failures, not pre-committed to a passing threshold.
- Incremental-revenue attribution for a promotion (FR-012) is computed via a
  defined, deterministic tagging in the test data (which orders a
  promotion drove), not statistical multi-touch attribution modeling — full
  marketing-attribution science is out of scope; the test data is
  constructed clean enough to demonstrate the mechanism honestly.
- The user wants this build to be usable with a real restaurant/bar's actual
  export files, not only this project's own CSVs — so ingestion parsing
  targets realistic, generic CSV shapes for each source type rather than a
  format hard-coded to this project's own exact columns. This is a design
  constraint for `/speckit-plan`, not a claim that real-file compatibility
  is validated in this build.
