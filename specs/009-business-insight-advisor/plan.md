# Implementation Plan: Business Insight Advisor

**Spec**: [spec.md](./spec.md) · **Status**: Ready for tasks/implementation

## Technical Context

A two-sided feature: a zero-cost deterministic teaser derivation added to the existing `/api/ask` response (backend Go, no model), and a new opt-in advice endpoint that makes one real Claude Sonnet 5 call when — and only when — the owner taps the teaser. One new persisted table, one new model constant, one new internal package for the model call, one new frontend chip component. No change to the gate, explain, cache, or paraphrase layers.

**Language/stack**: Go (backend, unchanged), React/TypeScript (frontend, unchanged), PostgreSQL via the existing `sqlc` + `golang-migrate` pipeline, Anthropic API via the existing shared `internal/llmclient`.

## Constitution Check

- **Principle I (deterministic/probabilistic split)**: The split runs through the middle of this feature by design. WHETHER an insight exists and WHAT it is about is plain Go over already-computed tool JSON (`deriveBusinessInsightTeaser`, zero model calls). The advice TEXT is openly probabilistic, opt-in, visually segregated, and explicitly labeled as a suggestion rather than a computed fact — it never produces a number the UI presents as computed, and the answer path is byte-identical with the feature present. ✅
- **Principle II (refuse rather than guess)**: The endpoint re-derives the teaser from the posted tool results and refuses (`insight_not_supported`) when they don't ground the requested kind; the prompt forbids invented restaurant-specific facts and fabricated statistics; unparseable tool JSON produces no teaser rather than a guessed one. ✅
- **Principle III (typed tools only, timeouts)**: The advice call reads NO data of its own — its entire grounding is the tool-result JSON the client posts back, which itself came from the typed MCP tools. It goes through the shared `llmclient.Client` (same 30s timeout policy), one call, no loop. ✅
- **Principle IV (provenance)**: The teaser is derived from tool results whose provenance is already on screen; the persisted ledger row stores the exact grounding JSON the advice was generated from; the UI labels the advice as a suggestion, which is the honest provenance statement for probabilistic content. ✅
- **Principle V (tests first / honest omission)**: Every trigger has both a fires-case and a does-not-fire-case test; the omission path (clean data → no teaser) is a first-class requirement (SC-001), not an afterthought. ✅
- **Principle VI (instrument every model interaction)**: Every advice call gets its own row in a NEW dedicated table, `business_insight_interaction` — the fourth distinct interaction type, for the same reason the first three are distinct tables (models.go: "so all states stay distinguishable and no cost is ever netted or hidden"). It is not the gate or explain running (so not `question_interaction`), not free (so not `answer_cache_hit`), and not a cache match (so not `paraphrase_match`). ✅

No violations requiring justification.

## Research grounding (Sourced vs. Judgment, per docs/product-strategy.md's tagging discipline)

- **[Sourced] Commission tiers and ranges**: OPA! Link, "Restaurant Delivery Commission Fees Explained (2025)" — DoorDash Basic 15% / Plus 25% / Premier 30%; Uber Eats 15–30% (30% standard marketplace); Grubhub 15–25% plus marketing fees, with total effective costs reaching 30%+. CloudKitchens, "How much do food delivery apps cost restaurants?" (2025) — 15–30% commission typical, plus 2–4% service/processing. Orders.co, "How To Negotiate Lower Commissions With Food Delivery Apps" — negotiation is a real, documented practice; volume strengthens the restaurant's hand.
- **[Sourced] Reconciliation discrepancy mechanics**: Voosh.ai, "The Multi-Unit Guide to Reconciling Third-Party Delivery Payouts" — the three documented root causes (platform-issued refunds/chargebacks silently deducted from later payouts; marketing/promotion deductions; "phantom" subscription/tablet fees), chargeback dispute windows "often 14 to 30 days", and daily-reconciliation-plus-prompt-dispute as the standard remediation. Restaurant365's automated-dispute-resolution product material corroborates the dispute-window pressure.
- **[Sourced] Cost-management practice for recurring expense patterns**: Restaurant365, "Essential Techniques for Controlling Restaurant Food Costs" and Toast, "Restaurant Inventory Management 101" — par levels sized to carry stock to the next delivery plus a buffer; a consistent counting/ordering cadence; reorder points tuned per ingredient class; delivery schedules as a lever, not a fixed constraint.
- **[Judgment — labeled as such in code]**: the exact `high_commission` cut (≥20.00% effective rate — five points above the published ~15% entry tiers, i.e. "paying materially above the entry tier", inside the sourced 15–30% band but not a number any source prescribes); the `day_of_month_expense_spike` outlier rule (highest average ≥1.5× the median day-of-month average, ≥2 occurrences); the `margin_decline` materiality rule (decline ≥5% of the prior period's absolute margin). Each constant's doc comment states its sourced anchor and its judgment cut separately.
- **Not used**: a widely-quoted "restaurants keep ~52% on discounted delivery orders" figure (Restaurant Business Online) could not be verified against the original article (fetch blocked), so it is deliberately NOT baked into any prompt or threshold — the negative-promo-ROI prompt sticks to incrementality/discount-depth practice that needs no unverified statistic.

## Per-component technical approach

### Deterministic teaser (FR-001..FR-008) — `backend/internal/httpapi/business_insight.go`

`deriveBusinessInsightTeaser(invocations []explain.ToolInvocation) *BusinessInsightTeaser`, modeled directly on `suggestions.go`'s `deriveFollowUpSuggestions`: group raw results `byTool`, parse each candidate with its own NARROW parse struct (the package's established convention — `discrepancyFlagsJSON`, `platformComparisonPeriodJSON`), and return the FIRST matching kind in a fixed priority order mirroring the existing "narrowest subject wins" switch: `compare_platform_economics` (high_commission) → promotions tools (negative_promo_roi) → `list_discrepancies` (discrepancy_pattern) → `get_margin_delta` (margin_decline) → `get_expense_pattern_by_day_of_month` (day_of_month_expense_spike) → `get_period_totals` (margin_decline on a real loss) — plus, additively (like `flagBasedFollowUp`), a `get_daily_summary` discrepancy-flag check when no primary tool matched. One teaser max; nil for clean/unparseable/unrecognized data. Money/percent strings are parsed with `internal/money.ParseCents`/`ParseFixedPoint` (comparison only — no new arithmetic path). New field on `AskResponse`: `BusinessInsight *BusinessInsightTeaser` with `json:"business_insight,omitempty"`, populated only at the `Status: "answered"` construction site.

### Advice model call (FR-010, FR-011) — new package `backend/internal/advisor`

Follows `internal/paraphrase`'s package shape exactly: a small struct over the shared `*llmclient.Client`, one `Advise(ctx, kind, toolResults)` method, its own `MaxOutputTokens`, its own system prompt, returns `{Text, InputTokens, OutputTokens, EstimatedCostUSD, LatencyMs}` for the caller to instrument. The system prompt is a shared safety base (never invent restaurant-specific facts beyond the provided JSON, never fabricate statistics or named sources, stay general/best-practice, stay short) plus a per-kind guidance section embedding the researched practice above. Model: new `llmclient.ModelBusinessInsight = "claude-sonnet-5"` constant with a doc comment in `cost.go` following the existing `ModelAmbiguityGate`/`ModelExplanation`/`ModelParaphraseMatch` documentation style — an advisory/reasoning task, not cheap classification, priced by the existing shared `"claude-sonnet-5"` map entry (same dedup rationale `ModelExplanation` already documents). Error contract mirrors `ambiguity.Gate.Classify`'s documented `(nil, err)`-on-every-failure shape (including a model refusal), which `ask.go` already documents as "no partial usage to log".

### Endpoint + ledger (FR-009, FR-012) — `POST /api/business-insight`

Handler in `business_insight.go` (`HandleBusinessInsight(deps)`), with an `Adviser` interface (like `Classifier`/`Narrator`) so tests can count/control calls without the live API. Flow: method check → decode `{kind, tool_calls}` → validate kind against the closed set → **re-derive** the teaser from the posted tool results and require the same kind (spec SC-005 — the same "never act on a client claim without re-verification" discipline `serveFromParaphraseMatch` documents) → `Advise` → write one `business_insight_interaction` row (log-loudly-on-failure, same as `logOrWarn`) → respond `{kind, advice_text, disclaimer, interaction}`. New migration `000010_business_insight_interaction` (kind CHECK-constrained to the five values, grounding JSONB, advice text, model, tokens, NUMERIC(12,6) cost, latency, timestamp — the `paraphrase_match` migration's commenting style), a new `queries/business_insight_interaction.sql` (Create/Sum/Count), regenerated via `sqlc generate`. Wired in `cmd/server/main.go` alongside `/api/ask`, sharing the same `llmclient.New()` client instance.

### Frontend (FR-013..FR-015)

New `frontend/src/components/Chat/BusinessInsightChip.tsx`: renders the title-only chip (lightbulb icon, explicit "AI suggestion" labeling, dashed/warning-tinted treatment — deliberately NOT the answer card's `border-border bg-card`), fetches on first tap only via a `resolveBusinessInsight` prop, shows loading/error states, expands inline with the advice text, the disclosure line, and the real cost (`$X.XXX · model`), and toggles open/closed thereafter without re-fetching. `ChatPanel.tsx` gains an optional `resolveBusinessInsight` prop (the same dependency-injection shape `resolveAnswer` already uses) and renders the chip in `AnswerBubble` after the follow-ups block when `message.businessInsight` is present. `AskPage.tsx` supplies the real resolver over `postJson('/api/business-insight')` and logs the returned interaction into the shared cost panel, exactly as `/api/ask` interactions already are.

## Testing strategy

Backend: table-driven tests for `deriveBusinessInsightTeaser` in `business_insight_test.go` — every kind's fires case, its does-not-fire case (clean data / below threshold / boundary), the priority order when multiple tools ran, and the nil cases (no tools, unparseable JSON) — using real tool-result-shaped JSON samples, `suggestions_test.go`'s style. Handler tests with a fake `Adviser` + recording store (the `ask_cache_test.go` counting-double pattern): success path (advice + cost returned, one ledger row with matching figures), kind-mismatch refusal, unknown kind, wrong method, adviser failure. A live-Postgres test (skip without `DATABASE_URL`, `reconciliation_tools_test.go`'s gating) proving the new sqlc queries round-trip against the real migrated table. Frontend: `ChatPanel.test.tsx` additions — chip renders when `businessInsight` present, absent when not, zero fetches on render, tap → loading → advice + cost + disclosure, collapse/expand without a second resolver call, error state on a rejected resolver.

## Open questions for implementation review (not blocking)

- Whether the teaser title strings should eventually localize alongside any future i18n pass — out of scope here, English-only like every other string.
- Whether advice calls ever warrant caching (deliberately not in this pass — see spec Assumptions).
