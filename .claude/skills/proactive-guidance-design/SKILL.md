# Designing proactive guidance before and after success

## Why this exists

A conversational interface can get refusal and clarification exactly right —
honest about what it can't do, always handing back a next step — and still
fail its user at the moment it *succeeds*. An answer that lands correctly and
then leaves the composer empty reads as "done," not as "here's what I'd check
next." The user is handed a correct number and then has to reconstruct, from
scratch, what a reasonable follow-up question even looks like. For a returning
user that's friction; for a first-time user staring at an empty composer
before they've asked anything, it's often the difference between typing a
question and closing the tab.

This is the mirror image of the recovery problem covered by
**question-recovery-design**: that skill is about the moment things go
*wrong* (ambiguous, unanswerable, refused); this one is about the moments
things go *right* — the zero state before the first question, and the instant
after an answer lands. Both are the same underlying insight applied to
opposite halves of the interaction: a conversational surface that only
handles one half well still strands its user at the other.

The gap is concrete, not hypothetical, and this project shows both its old
and its closing state at once. The chat surface already does the zero-state
half well — `EmptyState` in `frontend/src/components/Chat/ChatPanel.tsx`
shows three honest, tool-backed example questions before anything is typed.
The backend now computes the other half too: `backend/internal/httpapi/
ask.go`'s `AskResponse` carries a `SuggestedFollowUps []string` field,
populated by `suggestions.go`'s `deriveFollowUpSuggestions` for every
successfully answered interaction. But as of this writing the frontend has
not caught up — `AnswerBubble` in `ChatPanel.tsx` still ends after its
provenance tag and cache badge with no chip rendered from that field, so a
real, computed follow-up already exists on the wire and simply isn't shown.
That's the precise, current-state version of the dead end this skill exists
to close: not a missing capability, but an unrendered one. Treat "what do we
show after success" as the same first-class product surface the sibling
skill treats "what do we show after failure" — not an afterthought bolted on
once the happy path already works.

## The four moves

### 1. Zero-state capability transparency

Before the user has typed anything, a vague "How can I help?" forces them to
guess at the product's actual capability boundary — which, for a system with
a fixed set of typed tools rather than open-ended reasoning, is a boundary
that genuinely exists and can be stated exactly. Replace the vague prompt with
**3 named, provably-answerable examples**, each one tied to a real capability
the system actually has.

The non-negotiable rule, taken directly from
`frontend/src/components/Chat/exampleQuestions.ts`'s own doc comment:

> suggesting a question the product cannot answer is the same class of lie as
> inventing a number.

That file's `EXAMPLE_QUESTIONS` constant is the concrete pattern: every entry
pairs example text with the exact MCP tool name that answers it
(`get_daily_summary`, `get_margin_delta`, `list_discrepancies`,
`get_promotion_roi`, `list_negative_roi_promotions`,
`compare_platform_economics`), and the list is hand-written, versioned, and
changed only when a tool is added — never generated by asking the model to
describe its own capabilities. A model asked "what can you do?" will happily
invent something plausible-sounding and false ("compare your food costs to
industry benchmarks" is the file's own example of the failure). A suggestion
is a promise the product can keep; if there's no tool behind it, it isn't a
suggestion, it's a hallucination with a friendlier font.

The same file also derives `CAPABILITY_SUMMARY` (a one-sentence description
of scope) and `COVERAGE_PERIOD` (the exact date range covered) as constants
computed once from the same tool set, rather than as separate hand-tuned copy
that could drift out of sync with the examples above it. One source of truth,
several presentations.

### 2. Grounded follow-up suggestions

The moment right after a successful answer is the single richest context the
product will ever have about what the user might want next: it knows exactly
which tool ran, with which arguments, and what it returned. Waste that
context and you're back to a generic "anything else?" Use it, and the
follow-up can be genuinely specific.

**Derive, don't generate.** `backend/internal/httpapi/suggestions.go`'s
`deriveFollowUpSuggestions` is a real, landed implementation of this move,
and its own doc comment states the reasoning as directly as
`visualization.go`'s does: asking a model "what should the owner ask next?"
would be exactly the hallucination surface `exampleQuestions.ts` already
forbids — a free-text "what next" call has no typed tool backing it, so
nothing stops it from inventing a question the product cannot actually
answer — and it would bill a second, unnecessary model call on every single
answered question, against this project's own cost-discipline requirement.
So the function takes `[]explain.ToolInvocation`, `askedQuestion`, and the
real `dataStart`/`dataEnd` range, groups results by tool name exactly the way
`deriveVisualization` does, and picks a template based on a **fixed priority
order** — narrowest subject wins, mirroring `deriveVisualization`'s own
convention exactly, down to inserting `get_period_totals` just above
`get_daily_summary` because a period-level summary is still the least
specific "just tell me what happened" shape short of a single day.

Two disciplines worth calling out because they generalize past this project:

- **Clamp every generated date/period into the real data range.**
  `suggestions.go`'s `dateBounds` clamps every suggested date into
  `[dataStart, dataEnd]` — the actual reconciled range — so a "zoom out to
  the prior week" suggestion is never offered if the prior week doesn't
  exist in the data at all (`weekOverWeekAround` omits the suggestion
  entirely in that case, rather than clamping it into a misleadingly short
  span). A follow-up suggesting a question the product would then have to
  *refuse* is worse than no follow-up.
- **No groundable data → zero suggestions, not a placeholder.**
  `discrepancyFollowUps` returns nothing for a clean period, specifically
  because `list_discrepancies`'s result never echoes back which period was
  asked about — only which days were flagged — so there is no real date to
  ground a suggestion in, and the function's doc comment calls the empty
  result "a correct, honest outcome, not a bug to work around." Omission is
  a legitimate, designed output, exactly like `deriveVisualization` omitting
  the `Visualization` field entirely rather than rendering an empty chart.

**Cap tightly, and let one suggestion zoom in while another zooms out.** This
project caps at `MaxFollowUpSuggestions = 3` (the doc comment cites
Perplexity's and ChatGPT's follow-up row as precedent); as general guidance
elsewhere, 2–4 is the right range. The realized shape, quoting the actual
generated text:

- After `get_daily_summary` — **zoom in**: `"Were there any discrepancies on
  {date}?"` (same date). **Zoom out**: `"How did {prior week} compare to
  {this week}?"`, only offered when that prior week actually exists in the
  data.
- After `list_discrepancies` (flagged days present) — **zoom in**: `"What
  was the full daily summary for {latest flagged date}?"`. **Zoom out**: the
  same week-over-week comparison anchored on that date.
- After `compare_platform_economics` — **zoom in**: `"Were there any
  promotions with negative ROI between {period}?"`. **Zoom out**: `"What
  were the full totals for {period}?"` plus a discrepancies check over the
  same period.
- After `get_period_totals` — points at the period's own **best day** and
  **worst day** by name (`"What happened on {date}, the best/worst day in
  that period?"`) rather than an arbitrary date, since the tool already
  computed which two days mattered; the worst-day suggestion is skipped
  when it's the same date as the best day, avoiding a near-duplicate.

Every suggestion's date or period is a real value pulled out of the tool's
own JSON result — never a placeholder like "last week" — and
`finalizeSuggestions` additionally drops anything blank, drops an exact
(case/whitespace-insensitive) duplicate of the question the user just asked,
and de-duplicates before applying the final cap.

**Suggestions are ordinary replies, not a side door.** A suggestion chip
selected by the user must re-enter the exact same path a typed question
would: the same classification/ambiguity gate, the same tool-calling step,
the same instrumentation log entry. `ChatPanel.tsx` already establishes this
precedent everywhere `SuggestionChips` appears — every `onSelect` /
`onSuggestionSelect` handler is wired to `submitQuestion`, the same function
the composer's own submit button calls (see `RefusalBubble`'s
`onSuggestionSelect={submitQuestion}` and `EmptyState`'s
`onSelect={submitQuestion}` in `ChatPanel.tsx`). A follow-up suggestion must
be held to the identical rule: it is a pre-filled string that goes through
`submitQuestion` like anything else, never a shortcut that skips the
ambiguity gate "because the backend already vouches for it."

### 3. One suggestion component, one voice

The zero-state examples, the post-answer follow-up, and the post-refusal
recovery chips (see **question-recovery-design**'s move 5) are the same
underlying idea — "here's something concrete you could ask next" — appearing
at three different moments. They should render through **one** presentation
component, so a returning user recognizes the mechanism rather than meeting
three different lookalike UI patterns bolted on separately.

This project already has that component:
`frontend/src/components/Chat/SuggestionChips.tsx`, whose own doc comment
states the intent directly — "the single presentation for capability guidance
everywhere it appears." It's already reused across three placements in
`ChatPanel.tsx`: `EmptyState` (full list, `showTool` on, so a new user can see
which tool backs each example), `RefusalBubble` (first three examples,
`showTool` off, denser context), and the persistent "Ideas" panel opened from
the composer (full list, `showTool` on, for a user who wants a reminder mid-
conversation). When the post-answer follow-up ships, it is a **fourth
placement of the same component**, not a new one — likely with `showTool`
off, since a follow-up already carries context and doesn't need the tool name
spelled out. Resist the urge to give the post-answer chips their own visual
treatment "because they're contextual now" — the whole value of the shared
component is that guidance reads as one voice throughout the product.

### 4. Context-aware selection over static lists

`EXAMPLE_QUESTIONS` is static by design — at the true zero state there is no
context yet to compute from, so a fixed, hand-verified list is not a
shortcut, it's the correct answer. But a static list is the wrong tool the
moment real context exists: the follow-up shown after a `get_daily_summary`
call for `2026-08-07` should not be the same three chips shown to every user
regardless of what they just asked. Suggestions computed from real, current
state — which tool ran, what arguments it took, what page or view is open —
are strictly more useful than a list that never changes, because they get
more specific exactly when the user has given the product more to work with.

Decision guide:

| Situation | Use |
|---|---|
| True zero state — no question asked yet, no result to derive from | Static list (`EXAMPLE_QUESTIONS`) |
| Post-refusal recovery — no successful result exists this turn | Static list (a subset), per **question-recovery-design** |
| Post-answer follow-up — a real tool + result exists | Dynamic derivation (`deriveFollowUpSuggestions`, per Move 2) |
| A page/view with its own fixed scope (e.g. a single campaign's detail page) | Dynamic derivation scoped to that page's known entities |

The engineering cost of dynamic derivation is real — it's a new function,
tested against every tool's result shape, not a constant array — so don't
reach for it where the static list is already correct. Reach for it exactly
where context exists and a static list would visibly ignore it.

## Checklist

Use this when designing or reviewing the success half of a free-form-input
surface:

- [ ] Does the zero state show 3 (not zero, not a dozen) named example
      questions, each tied to a real, currently-implemented capability?
- [ ] Is the zero-state list hand-written and versioned, never generated by
      asking the model to describe its own capabilities?
- [ ] Does every successful answer offer at least one follow-up suggestion,
      so no answer is a hard dead end the way a blank composer is?
- [ ] Are follow-up suggestions derived deterministically from the real tool
      name + arguments + result of the interaction that just ran, rather
      than a second model call guessing at what might be useful?
- [ ] Is the follow-up count capped (2–4), with a bias toward one "zoom in"
      (refine within the same result) and one "zoom out" (a related, broader
      question)?
- [ ] Do the zero-state examples, post-answer follow-ups, and post-refusal
      recovery chips all render through the same presentation component and
      tone, rather than three separately-styled mechanisms?
- [ ] Does selecting any suggestion — zero-state, follow-up, or recovery —
      re-enter the exact same submission path a typed question would (same
      classification gate, same instrumentation), never a privileged
      shortcut?
- [ ] Is a static list reserved for genuine zero-context moments, with
      dynamic, state-derived suggestions used wherever real context (a tool
      result, a page scope) actually exists?
- [ ] Would omitting a suggestion (showing none) ever read better than
      showing a bad one? If so, is "no suggestion" a real, reachable outcome
      of the derivation — not just an oversight?

## Anti-patterns

| Anti-pattern | Why it fails |
|---|---|
| Model freelances its own capability description ("Ask me anything about your business!") | A model describing its own capabilities is a fresh hallucination surface — it will invent things it cannot actually do, which is the same class of lie as inventing a number. |
| A suggestion wall (6+ chips after every answer) | Turns a quick next step into a decision-paralysis exercise; defeats the purpose of a fast, low-effort follow-up. |
| Suggesting a question the product cannot actually answer | Breaks the exact trust a correct answer just built — the user learns the suggestions themselves can't be trusted. |
| A suggestion chip that bypasses classification/validation "because it's just a suggestion" | Creates a second, less-scrutinized path into the system; a suggestion is a pre-filled question, not a privileged command. |
| Post-answer chips get their own bespoke visual style | Fragments one underlying idea ("here's what to ask next") into three lookalike-but-different mechanisms instead of one recognizable voice. |
| Static suggestions reused verbatim after every answer regardless of what just happened | Ignores the richest context available (the real tool + result) and reads as generic rather than responsive. |
| Suggesting a follow-up with a placeholder argument ("check discrepancies for a date of your choosing") | Not actually derived from what happened — a suggestion is only as good as the concrete value it's grounded in. |

## Worked example (case study, not a template to copy verbatim)

This methodology was generalized from a real product-strategy review of a
restaurant margin-reconciliation copilot, referenced here to make the moves
concrete — adapt the *shape* of the pattern to your own stack, not these
exact files or tool names.

- **Move 1 (zero-state transparency):** `EXAMPLE_QUESTIONS` in
  `frontend/src/components/Chat/exampleQuestions.ts` pairs each example
  question with the exact MCP tool name that answers it — a fixed,
  hand-maintained list, never model-generated, with the explicit rule that a
  suggested-but-unanswerable question is the same class of dishonesty as a
  fabricated number. `CAPABILITY_SUMMARY` and `COVERAGE_PERIOD` are derived
  as constants from the same tool set so the prose description and the
  example list can never drift apart.
- **Move 2 (grounded follow-ups):**
  `backend/internal/httpapi/suggestions.go`'s `deriveFollowUpSuggestions`
  mirrors `visualization.go`'s `deriveVisualization` convention exactly —
  same fixed, narrowest-subject-wins tool priority, same plain-Go derivation
  with no second model call — and adds two disciplines of its own: every
  generated date/period is clamped into the real `[dataStart, dataEnd]`
  range so a suggestion never points at data that doesn't exist, and a tool
  result with nothing groundable to suggest from (a clean
  `list_discrepancies` result, which never echoes back its own period)
  produces zero suggestions, documented explicitly as a correct, honest
  outcome rather than a gap to patch.
- **Move 3 (one component, one voice):**
  `frontend/src/components/Chat/SuggestionChips.tsx` is reused, unmodified in
  shape, across three placements in `ChatPanel.tsx` — the empty state, the
  refusal-recovery bubble, and a persistent "Ideas" panel opened from the
  composer — each passing a different question list and a `showTool` toggle,
  but all rendering the same chip. Every placement's `onSelect` calls the one
  `submitQuestion` function the composer itself uses, so a chip is never a
  side door around classification.
- **Move 4 (static vs. dynamic):** the zero-state list is static because
  there is genuinely no context yet to compute from; the (planned) post-
  answer follow-up is dynamic because, by the time an answer exists, the
  richest possible context — the real tool, its real arguments, its real
  result — already does too, and a static list at that point would visibly
  waste it.
- **The gap that motivated this skill:** `AnswerBubble` in `ChatPanel.tsx`
  renders a successful answer's chip row, chart, text, and provenance, and
  then stops — no suggestion, no next step. The product had already solved
  "what do we show when things go wrong" (`RefusalBubble`) without yet
  solving the mirror-image problem of "what do we show right after things go
  right," which is precisely the dead-end-after-success gap this skill
  exists to close.

## Related skills

- **question-recovery-design** — the mirror-image skill, covering the moment
  a question goes *wrong* (ambiguous, unanswerable, refused) rather than the
  moment it goes right. Read it for the shared `SuggestionChips` component's
  refusal-time placement, and for why "show capabilities proactively" also
  appears there as move 5 — that move is this skill's Move 1, generalized to
  fire reactively as well as proactively.
- **ux-writing** — for the tone and wording of a follow-up suggestion's
  actual copy once the derivation logic has decided what to offer.
- **api-design** — for the equivalent discipline at a pure API boundary
  (what a successful response's "next steps" or "related resources" field
  should contain) when there's no chat surface to render a chip into.

## When this doesn't apply

Skip this for surfaces with no meaningful "next question" concept — a
single-purpose form that produces one final result and is done (a calculator,
a one-shot export), where offering a follow-up would be inventing engagement
rather than serving a real continuation of the user's task. This methodology
is for conversational or multi-turn surfaces where a successful answer is
naturally one stop on a longer path, not the whole trip.
