02 · Gamification

Badges are the UX answer to complexity — not decoration

A reconciliation tool genuinely has several distinct capabilities. For a time-poor, non-technical owner, badge-styled tiles double as the home screen's information architecture: the same visual language that quietly confirms "this worked" also answers "what can I do here."

Quiet, not arcade — grounded in real B2B research

  • Sourced Owners are "app-rich but insight-poor" — tools survive by being quick and daily, not impressive once.
  • Sourced B2B gamification that works is quiet acknowledgment — a bar fills, a banner notes it. Game-feel would undercut a financial tool's trust.
  • A typed Postgres enum, awarded by deterministic Go logic. The model narrates a badge — it never decides one.
  • Badge green is the semantic --success token — deliberately yellower than the brand emerald, so a badge never reads as brand.

03 · Demo — live, in three acts

Real backend, real Postgres, real model calls

The fixture data is two weeks of a fictional restaurant with the mess built in on purpose — a duplicate order, a cross-week refund, a missing day, two clashing date formats — every golden figure verified independently by hand before any code existed.

Open the app, see the day

The gate classifies, typed tools compute, Sonnet narrates — and the answer arrives with provenance and its own live line on the running cost panel.

Act 3 · A live refusal

"What's the ROI on the weekend campaign?"

IFOOD-CAMP-WEEKEND spent $95.00 — but its attribution breakdown is missing from the export, so the system refuses to assert an ROI rather than estimate one. The refusal is the feature.

roi → null · refusal, by design

Nothing here is a recording. Live database, live Anthropic API, a cost panel ticking up in real dollars — and at least one refusal is part of the script, because a confidently wrong figure is worse than one.

04 · Architecture

No number the owner sees is ever produced by a model

Arithmetic happens once, in Go, against Postgres. The model layer only ever receives the result of a typed tool call and narrates it — it cannot see raw rows and cannot query the database on its own terms.

Deterministic — code, no model, ground truth Probabilistic — model, interprets and narrates only Hard limit — refuses rather than guesses

Users, use cases, and risks

Persona: independent restaurant/bar owner-operator — time-poor, "app-rich but insight-poor," juggling POS + delivery platforms + spreadsheets. Needs glanceable, not a sit-down dashboard.

Use cases: 1 — daily close, no question required. 2 — ask "how did we do this week vs last?" and get a provenanced answer. 3 — an ambiguous or unanswerable question gets a clarification or refusal, never a guess. 4 — a money-losing promotion gets its ROI and provenance, or an honest "can't attribute this."

Top risk, as written before the run: "real harness numbers are worse than hoped" — mitigated by reporting honestly including failures, which the evaluator's own framework explicitly values. That is exactly what happened, and exactly what was done.

08 · Technical RFC — accepted

Engineered so the model can't break the numbers — at the lowest cost that holds the bar

Go 1.27 · PostgreSQL · React + TypeScript · anthropic-sdk-go · mark3labs/mcp-go in-process · sqlc + pgx/v5 · promptfoo. No agent framework — the brief asks for judgment, not orchestration.

Model per step — a cost/quality decision, documented

StepModelPrice in/out per MTokWhy
Ambiguity gateHaiku 4.5$1 / $5A cheap classification task over question text — the gate never touches real data at all.
ExplanationSonnet 5$2 / $10Narrates an already-computed number. No frontier reasoning needed — deliberately no Opus, no Fable here.
Arithmetic— none —$0Every number is Go against Postgres. A model is never in this path.

Live-spend control, as an operational mechanism

A hard $5 ceiling with a $4.50 checkpoint: smoke-test with a few instrumented calls, then run the harness as one monitored step. In the RFC — not a slide claim.

Five fixed MCP tools — and nothing else

get_daily_summary · get_margin_delta · list_discrepancies · get_promotion_roi · list_negative_roi_promotions — each read-only, timeout-bounded, returning a typed error instead of a best-guess value. No open-SQL or free-form-filter tool exists to be misused.

Design decision: a closed day never gets silently restated

Accrual, not cash: Aug 2 becomes $154.25 − $34.50 = $119.75. A same-day product can't let a late refund quietly rewrite a closed day — cash-basis was considered and rejected.

Alternatives that were genuinely close calls

Anthropic's native MCP connector (URL-based) instead of in-process mark3labs/mcp-go: would require the MCP server to be independently HTTP-reachable — an unneeded deployment step locally, noted as a real simplification if this ever moves to hosted.

A hand-rolled Go eval harness instead of promptfoo: viable, but promptfoo's assertions/repeat features map ~1:1 onto the three required evaluation axes — building one would be pure cost with no capability gain.

09 · User stories & acceptance criteria

Trust is earned in order — no story ships until the one before it is proven

4 user stories · 13 functional requirements · 3 persisted entities · 6 success criteria — every story independently testable, every scenario written before its code.

P1 · See the day, provenanced→ P2 · Ask in plain language→ P3 · Never guess→ P4 · Grow spend wisely the growth lever is built last, on a core already proven trustworthy

P1  See today's reconciled margin

The entire reason the product exists — nothing else matters if this number isn't right.

Acceptance
  • A clean day's margin matches manual computation exactly, with source citations.
  • A duplicate order isn't double-counted; a refund is netted — both visible in the provenance trail.
  • A missing source file is stated plainly, never silently omitted from the figure.

P2  Ask natural-language questions

What makes it daily-usable instead of a table to read — but it depends entirely on P1 being correct.

Acceptance
  • "This week vs last" returns the delta with the specific dates used.
  • Three phrasings of the same question agree.
  • Any computed number came from the reconciliation engine, never the model.

P3  Refuse or clarify instead of guessing

The direct demonstration of the central architectural bet — and the hardest thing to make an LLM system do reliably.

Acceptance
  • A question about absent data states what's missing rather than estimating.
  • An ambiguous date range triggers a clarifying question, or a stated assumption.
  • Exceeding the tool-call cap stops and reports — never a partial, unlabeled answer.

P4  Flag underperforming promotions

The growth-side half of the Objective, built last, on a core already proven trustworthy.

Acceptance
  • A negative-ROI promotion is reported with the orders and spend it was computed from.
  • A profitable one is not flagged, and states its positive ROI if asked.
  • Unattributable incremental revenue → refuse to assert an ROI. Same discipline, growth side.
FR-001–003 · ingest + reconcile, zero silent loss FR-004–005 · grounded answers, provenance on every number FR-006–007 · ambiguity gate, refuse over estimate FR-008–010 · full instrumentation, capped + timed tools FR-011–013 · promo ROI, refuse when unattributable 100% FR/SC → task coverage, verified pre-build
The 13 functional requirements, compressed

FR-001–003 ingest all three source types; reconcile duplicates, refunds, and clashing date formats with zero silent loss; compute week-over-week deltas with anomaly flags. FR-004–005 natural-language Q&A grounded in reconciled data, provenance on every number. FR-006–007 answerability/ambiguity gate before any answer; refuse rather than estimate. FR-008–010 per-interaction tokens/model/cost/latency/refusal logging, a visible running total, capped tool iterations with timeouts. FR-011–013 ingest promo spend; compute incremental-revenue-to-spend per campaign and flag negatives; refuse ROI when attribution is impossible.

Where it went wrong — and how it was caught

The sentinel-date collision that silently deleted $152.50

A test used a real in-range date as its fixture key; its cleanup DELETE destroyed the pipeline's real row. The agent reported 14 days persisted. Caught by an independent psql query — 13 rows, short by exactly 152.50.

The model was quietly doing arithmetic — and passing tests for it

No tool returned a combined delivery total; the model was summing the map itself — a Principle I violation that passing scores rewarded by accident. The honest fix was a deterministic Go field, not more prompt engineering.

My own git add -A, during an overnight session

A "cleanup" commit swept a background agent's half-finished edits onto main; briefly, the tree didn't build. Caught by running go build on principle. The misleading commit message stays in history — disclosed, not rewritten.
