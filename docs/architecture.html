Prototype architecture

Restaurant Margin Copilot

Daily close and margin alert for an independent restaurant. Ingests delivery-platform exports, POS exports, and a supplier cost sheet; reconciles them; and answers plain-language questions about the day and the week — flagging what changed and why, before the month closes and it's too late to act.

Go PostgreSQL MCP React Anthropic API ● setup in progress

The job to be done

The owner already receives all the numbers they need — a delivery-platform payout file, a POS export, a cost sheet — but nobody reconciles them daily, because it's tedious and error-prone by hand. Margin slippage is usually discovered when the month closes: too late to change anything about the week that already happened. This product closes that gap by doing the reconciliation automatically, every day, and letting the owner ask about it in plain language.

It is deliberately not a general restaurant assistant, not an empty chat box, and not a multi-agent system for its own sake. It is one narrow job, done in a way where every number is verifiable.

Where the line sits

The central design constraint: no number the user sees is ever produced by a model. Arithmetic happens once, in Go, against Postgres. The model layer only ever receives the result of a typed tool call and narrates it — it cannot see raw rows, and it cannot query the database on its own terms. Two later additions sit on the deterministic side of that same line: an exact-match answer cache in front of the ambiguity gate, so a repeated question makes no API call at all, and a chart-type decision behind the explanation step, so whether an answer arrives as a table, a bar chart or a pie is derived in Go from which tool ran — never asked of a second model.

Hard limits & soft limits

Hard limits

  • Refuses rather than estimates when data is missing or incomplete.
  • No open SQL, no free-form computation — defined, typed MCP tools only.
  • Chart selection is deterministic Go, from the tool name and result shape — never a second model call deciding how a financial figure is drawn.
  • The answer cache matches exact question text only (whitespace and case ignored). A paraphrase is a new question and pays full price — a disclosed limitation, not a bug: semantic matching would put a probabilistic step in front of a deterministic lookup, and serving the answer to a question nobody asked is worse than paying for the call.
  • A cache hit is the absence of a model interaction. It is never written to question_interaction, which would fabricate an API call and inflate the cost total, and never left unrecorded — it goes to its own answer_cache_hit ledger carrying the cost it avoided.
  • Timeout on every tool call; explicit cap on loop iterations.
  • Every number carries provenance: which file, which rows, which period.

Soft limits

  • The model is nudged toward the right framing, not hard-coded to one phrasing.
  • Free to self-correct on rephrasings and unexpected question shapes.
  • Clarifying questions are asked rather than assumptions being silently made.
  • Assumptions that are taken are always stated back to the user.

Build order

Deliberately sequenced — if the interface is polished before the numbers are right, the challenge is failed.

  1. Fixture data first, including the deliberate mess: a duplicate order, a refund, a missing day, an inconsistent date format.
  2. Deterministic reconciliation engine in Go, proven with tests — before any LLM call exists.
  3. MCP server wrapping the reconciliation engine as a fixed set of typed tools.
  4. Model layer, starting with the ambiguity gate.
  5. Instrumentation — tokens, cost, latency, refusal rate — from the first API call.
  6. Evaluation harness, before polishing the interface.
  7. React frontend last.
