Technical reference

Restaurant Margin Copilot

Daily close and margin alert for an independent restaurant. Go computes every number; two Claude models interpret the question and narrate the answer, and neither ever does arithmetic. This is the reference for how that is actually built — the design system it ships with, the deterministic engine underneath it, and the whole system with its limits stated rather than hidden.

Go 1.x PostgreSQL 16 MCP · mark3labs/mcp-go React · Vite · Tailwind v4 Claude Haiku 4.5 + Sonnet 5 ● prototype, single instance

Everything below is what frontend/src/index.css and the components around it actually ship today — read out of the source, not proposed. The app is My Business Steward; the repository and this document keep the working name.

The honesty pattern

One component convention matters more than any colour rule here, because it is how this product handles the gap between what is built and what is pitched. PointsCard.tsx puts a real, derived balance and an explicitly-labelled roadmap block in the same card, in the same voice, separated visually by a border and a muted ground. The roadmap half is written as a destination, not as a disabled button: there is nothing to click, and pretending otherwise would be exactly the fabricated capability the whole product refuses to ship.

The same split is used on this page's third tab, for the same reason.

The rule in one line. If a figure is real, show it and cite it. If it is not built, say so in the same breath, in the same card, and give it a visual treatment that cannot be mistaken for a live control.

This is the part of the system that produces every number the product will ever show. It is ordinary Go, run from a CLI flag, against ordinary Postgres.

Zero model involvement in anything on this tab. No Anthropic API key is needed to run any of it. No prompt exists in any of these packages. internal/reconcile does no I/O at all — it takes parsed records and returns computed structs, and it does not know that Postgres, MCP, or Claude exist. It was built and proven with tests before the first LLM call existed in the repository, which is the whole reason the numbers can be trusted later.

The pipeline

Deterministic — code, no model, ground truth Hard limit — refuses rather than guesses
Still zero model involvement. The connector layer below is ordinary Go: a seeded pseudorandom order model, two JSON decoders, and a contract check. No prompt, no API key, no Anthropic call anywhere in the fetch, the normalization, or the reconciliation that follows it. It is a new source, not a new kind of computation.

Stage 1, second route: the Connector Proxy

All three upstreams below are simulated. This project has no iFood partner-API credentials, no Just Eat Takeaway partner-API credentials, and no POS terminal to poll, and will not have them. Every order the connector returns is generated locally from a seeded model. What is real is everything between the mock upstreams and the reconciliation engine — the interfaces, the three adapters, the normalization, the contract checks, and the cross-source deduplication — and it is real because a mock is only worth building if the thing sitting on top of it is the thing you actually mean to ship.

The three mocks are deliberately incompatible with each other. That is the entire point: a proxy over APIs that already agreed would be a rename. iFood speaks page-numbered JSON in snake_case, with money as decimal strings inside nested currency objects, RFC 3339 timestamps carrying the merchant’s offset, an explicit rate_percent, and a cancelled order reported with positive amounts alongside a cancellation block. Just Eat Takeaway speaks cursor-paginated JSON in camelCase, with money as integer minor units, epoch-millisecond timestamps in UTC, no commission rate at all, and a refund reported already negative. The POS speaks newline-delimited JSON with no envelope and no pagination at all, money in pt-BR notation ("1.234,56"), zone-less local timestamps, PAID/VOID, and a nested delivery_partner block on any ticket that arrived through an aggregator.

Deterministic — code, no model, ground truth Simulated — stands in for a source this project has no access to

Why the mocks emit real JSON bytes. Each mock marshals to []byte and its adapter unmarshals it back. Skipping that round trip would be simpler and would also make the whole exercise vacuous — if the mock handed back records the adapter merely copied, there would be no normalization to demonstrate. The heterogeneity has to exist on the wire for the work to be real. It is the one place this feature spends complexity on purpose.

Two conversions carry the actual risk, and both fail silently rather than loudly if they are wrong. Just Eat Takeaway reports no commission rate, but DeliveryRecord.CommissionRateBps is what reconcile.recomputeCommissionCents independently cross-checks against — derive it wrong and every JET order raises a commission_mismatch flag, burying the genuine discrepancies under integration noise. And the two platforms disagree about the sign of a refund, so one adapter negates and the other must not — get that wrong and a refund is counted as revenue, raising a day’s margin because money went out. Contract checks 3 and 5 exist because of exactly these two.

Determinism, and why it is not a shortcut. Each (platform, date) pair seeds its own generator from an FNV-64a hash of a fixed salt, the platform key, and the date. cmd/gendata uses a single seeded stream consumed in file order, which is right for generating a dataset once, top to bottom; it is wrong here, because a connector fetch is random access. An owner may sync one day, or five, or the same day twice, in either platform order — and with a shared stream the same date would return different orders depending on what had been fetched before it, so the same day would reconcile to a different margin depending on the order someone happened to click in. Hashing the key into its own seed makes every day an independent, order-insensitive draw.

The third source, and the problem it creates

The POS is two thirds of this restaurant’s gross sales, and adding it as a connector source is the easy half of specs/012-pos-connector-dedup. The hard half is what adding it exposes. A POS that integrates with a delivery aggregator — which is why front-of-house sees one screen and one kitchen printer — has the aggregator’s orders pushed into it, where they become POS tickets with their own POS order numbers. The same real-world order then arrives twice in one sync: once in the platform’s settlement feed, once in the POS’s ticket feed. Sum both and gross sales inflate, the cost ratio understates, and the margin percentage reads better than reality every single day.

Measured on this product’s own data for 2026-08-18..20: naively summing the three sources gives $14,285.89 of gross sales against a true $12,442.88 — $1,843.01 counted twice, and a three-day margin overstated by 20.3%.

The inverse failure is the harder one to design against. A matcher that is too eager merges two genuinely different orders that happen to share a price and a rough time. On a 20-to-30-order evening at a $32 mean ticket that is not exotic, it is expected — and the result is real revenue deleted from the day, unrecoverable from the reconciliation output, and invisible, because the day is simply lower and nothing says why. Dropping a real order and double-counting a duplicate one are the same financial-integrity failure wearing different signs.

A POS ticket is a duplicate of a delivery order only if the POS itself said the ticket arrived through a delivery channel. Within that set: if the ticket carries the platform’s order reference and that reference resolves, they are the same order. Otherwise they are the same order only if they share a platform, a calendar date and an exact amount in cents, their times are within 15 minutes, and no other reading of the day’s tickets is equally consistent.

Three consequences, each a deliberate choice rather than a fallout of implementation. No matching on amount and time alone: without an assertion from one of the two systems that a delivery channel was involved, the evidence is “these numbers are similar”, and acting on that deletes revenue — so an untagged dine-in ticket is ineligible at any amount, at any time, forever. Ambiguity is disclosed, never resolved by preference: where one ticket has two candidate orders, or two tickets contest one, nothing merges, every record survives, and the day carries a flag naming the candidates; the pairing must be the unique solution from both directions, which is also what makes the outcome independent of iteration order rather than a coin flip dressed as an answer. The delivery record wins: it knows the commission, the rate, the payout and the refund state, where the POS ticket knows only a gross amount — dropping the delivery side would zero that order’s commission and move margin up, a wrong number in the flattering direction.

Still zero model involvement, and this is the part worth pointing at in a demo. “Work out whether these two records are the same order” is exactly the shape of problem a language model would be reached for, and exactly the shape this product refuses to hand one. The matcher is integer-cent equality, case-folded string equality, and a minute difference. Every decision it makes can be recomputed by hand from the two records involved — which is what auditable has to mean when the output is money.

The simulation is built to make the rule work for its living. The POS mock does not invent delivery-looking tickets; for each date it calls the same generator the iFood mock calls and echoes those actual orders, so a duplicate the matcher finds is causally real rather than a coincidence the mock arranged. Around it sit the deliberate difficulties: only iFood is integrated into the POS and Just Eat Takeaway is not, which puts a control group inside every fetch; a quarter of echoed tickets carry no partner reference, so the harder matching tier is not decoration; and campaign-discounted orders disagree on amount because the POS rang the menu price and never saw the platform’s promotion. Ambiguity is not manufactured — the mock does not arrange a collision so a flag has something to do, and the real incidence is reported as measured. Over August 2026, all 31 days, three sources: 689 duplicates resolved, 40 overlaps left unresolved and flagged, and 2,569 in-house tickets, every one of them intact. Zero false positives is a test that runs on every build, not a claim.

Nothing is silently corrected. Every outcome reaches the day it affected as a discrepancy flag in the vocabulary internal/reconcile already uses — cross_source_duplicate_removed, cross_source_duplicate_unresolved, cross_source_amount_mismatch — each naming both sides: which ticket was removed, which order it merged into, at which row of which source. An unresolved overlap states the consequence out loud: “this day may count that order twice.” The connected-sources panel reports the removals and the unresolved overlaps side by side, because reporting only the removals would let the product claim a clean close it did not achieve.

What is still not built

From an emulated connector to a real feed

The connector layer above is built and exercised; the credentials are not, and neither is any of the operational machinery a real feed needs. Deliberately absent, each for a stated reason: no OAuth, token refresh, or credential storage (there is no credential — an auth flow against a fake upstream validates nothing and would misrepresent how far along the integration is); no retries, backoff, rate limiting, or circuit breaking (in-process function calls do not fail transiently, and simulating flakiness so resilience code has something to catch would be fiction stacked on fiction); no webhooks or scheduling (pull-on-demand only, from a button an owner presses); no fourth source and no plugin registry (exactly three, registered explicitly); no deduplication on the CSV upload path (a file exported by hand from a POS with no delivery integration has no overlap to find, and this product has no way to know which kind of POS produced a given file — guessing would be estimating).

The original roadmap entry, kept — the strategic move has not changed

Closing the manual-file gap: direct platform feeds, not just direct upload

Stage 1's sources still arrive as files by default — a delivery-platform export, a POS export, a supplier cost sheet — and spec 007 already replaced one manual step (a developer running -ingest from a terminal) with a web upload. The connector above replaces a second one, for delivery revenue, against upstreams that are emulated. The objective that remains genuinely unbuilt is doing it against the real thing: a scheduled Go worker pulling each day's confirmed orders and settlement data from the actual iFood and Just Eat Takeaway merchant/partner APIs under real credentials, normalizing the response into the exact typed record shape stage 2's parser already produces, and handing it to stage 3 completely unchanged. The shape of that work is now built and tested; what is missing is partner access, a scheduler, and the settlement-timing handling below. The API replaces file arrival, nothing downstream — Claude still never touches arithmetic, and Go still computes every margin. The supplier cost sheet gets the equivalent treatment from the other direction: invoice photo/PDF capture with Claude vision extracting into the same typed shape, then direct supplier feeds through Prosus's own merchant network. Both are one strategic move viewed from two sides: every number this pipeline consumes stops arriving as a manually produced file.

Why this is roadmap, not backlog. iFood integration is comparatively warm — it operates a real merchant developer platform in Brazil, and inside Prosus this is an internal conversation rather than a cold partner ask. Just Eat Takeaway's merchant integrations run through an approved-partner program, so it follows rather than leads. Sequenced after the cost-sheet's OCR phase specifically because OCR is a capability this product controls end-to-end and can ship unilaterally; API access depends on a partner-approval process outside engineering's control.

The honest risk, named rather than sold past: a platform's real-time order feed and its end-of-period payout statement — where actual commission, refunds, and adjustments land — routinely disagree for days. Per this system's own refuse-rather-than-guess discipline, a day whose settlement data hasn't arrived would be flagged provisional, never silently estimated. “Automated” would not mean “instant.”

The five discrepancy flags, in full

The dataset’s hand-authored opening window contains deliberate mess — a duplicate order, a refund, a missing day, an inconsistent date format — because the mess is what makes reconciliation logic worth showing. Each flag names what happened and which rows it happened to, so an adjustment is never silent.

FlagFires whenWhat the engine does
duplicate_order_removed Two delivery rows are identical across platform, order id, timestamps, all amounts, status, campaign and notes. Counts it once. The flag names both row numbers and the file. Treated as an export or webhook-retry glitch, not a second line item.
missing_delivery_source A calendar day has POS or cost data but zero delivery rows. Still produces a reconciliation for that day from whatever sources exist. Delivery revenue is absent, not zeroed, and the day is excluded from every other day's anomaly baseline.
commission_mismatch The file's own commission_amount differs by more than a cent from subtotal × rate. Uses the recomputed figure and flags the discrepancy with both values. The file's number is checked, never trusted.
pos_non_completed_row_excluded A POS row carries a status other than completed (or blank). Excludes it from gross sales and says so, rather than quietly including or dropping it.
anomaly_threshold_exceeded Total gross revenue deviates more than 20% from a trailing 3-day average of complete days. Flags the day with the actual figures and the threshold. At the dataset's realistic scale, ordinary weekly seasonality can legitimately cross 20% (a slow Monday after a strong weekend does), and the reconciliation tests pin exactly which opening-window days do — tunable, not asserted as universal.

Modelling choices that are visible on purpose

Supplier costs are point-allocated

Costs land on their own invoice date only — no smoothing or amortisation across the gap to the next invoice. Real supplier billing isn't daily, so a day without an invoice contributes zero input cost. That is a known, visible modelling choice, not a hidden average.

Refunds net to the original order date

Not the settlement date. Platform exports carry order_date as the original order's date, so netting there keeps the day's margin honest. Gross sales report completed bookings only; refunds are a separate field.

Attribution is a tagging convention

Promotion ROI is a tag-join on campaign_id, not statistical multi-touch attribution modelling. It is deterministic and reproducible, and it is stated as a convention rather than presented as a causal claim.

Money is integer cents, everywhere

internal/money owns every conversion; float64 never touches a currency amount. Even the dollar value the chart layer uses for bar heights is derived from cents by that package, not by a JavaScript parse of a formatted string.

Why it was built first

The build order was fixed before anything was written, and not reordered:

  1. Hand-authored test data, including the deliberate mess.
  2. The deterministic reconciliation engine in Go, proven with tests — before any LLM call existed.
  3. The MCP server, wrapping that engine as a fixed set of typed tools.
  4. The model layer, starting with the ambiguity gate.
  5. Instrumentation — tokens, cost, latency, refusal rate — from the first API call.
  6. The evaluation harness, before polishing the interface.
  7. The React frontend, last.

If the demo is beautiful and the numbers are wrong, the challenge is failed. This ordering is the mechanism that prevents it.

One Go process, one Postgres database, one React app, and two Claude models across three separate model pathways: the ask pipeline (gate, conditional writer, explanation), the paraphrase check in front of the cache, and the business-insight advisor with its own ledger — reached by tapping a teaser behind its own endpoint, or inline when a question explicitly asks for advice. Below is all of it, including the parts that are not built.

The system, top to bottom

Three groups of UI surface sit on three groups of HTTP surface, and all of them read the same Postgres. Only the first group has a model anywhere in its request path — and inside that group, the two endpoints are drawn apart, because one is the ask pipeline and the other is the opt-in advisor, which is a different kind of thing and bills separately.

Inside POST /api/ask

Six named steps. The gate and Explain are always-model steps; the date-range pre-check, the MCP tool layer and the chart-type decision are always plain Go. The Answer cache step is mostly plain Go too — a free exact-text lookup on every call — but conditionally makes one small, real, billed Haiku call of its own on a miss, to check for a paraphrase before falling through to the gate. That call is disclosed the same way every other model call is: logged, costed, and never presented as free. The boundary in this system is not a line on a map but a rule about what each step is permitted to do.

Deterministic — code, no model, ground truth Probabilistic — model, interprets and narrates only Hard limit — refuses rather than guesses

Two models, and every job each one is trusted with

Claude Sonnet 5 — the ambiguity gate (moved off Haiku 4.5, 2026-08-29)

internal/ambiguity. Classifies one question, before anything runs, into answerable / ambiguous / unanswerable, and emits a small fixed JSON object — never prose. Capped at 2560 output tokens — raised three times from the original 512 (512 → 768 → 1536 → 2560), each time after a real live truncation, not as precautionary headroom: first on a compound multi-part question, then on a question whose refusal reason is composed inside this same call, which has to classify and write a specific explanation of what is missing within one budget, and most recently (2026-08-30) on "How was the weekend?" — an ambiguous verdict is the real worst case, since it must classify and then compose both a clarifying question and its options inside the one budget. A response that still hits the cap is caught explicitly by a stop_reason check, never silently trusted. The conditional writer pass keeps its own, smaller 768 cap. (That second Sonnet 5 call is described in the callout below.)

  • Why not the cheap model anymore: this ran on Haiku 4.5 for the original single-year window, where classification didn't need frontier reasoning. Once the live dataset grew to span 2024–2026, Haiku repeatedly misclassified fully in-range, explicitly-dated questions (e.g. “July 2026”) as unanswerable — a real date-comparison failure across a year boundary, not a prompt-wording issue. Three prompt-only fixes were tried and verified not to fix it; swapping this one call to Sonnet 5 fixed it immediately. Full rationale in internal/llmclient/cost.go's doc comment.
  • Why it cannot leak a number: the package has no import path to internal/storage or internal/mcptools at all. It sees question text and nothing else. The one exception is deliberate and narrow — it is handed the data's real min/max date range as two plain strings, so “today” grounds against what the data covers rather than the host machine's clock.
  • On ambiguity it either asks a clarifying question or proceeds with the assumption stated back to the user. It never silently assumes.

Claude Sonnet 5 — the explanation step

internal/explain. Owns a tool-calling loop against the typed MCP tools — direct Anthropic API calls with the tool definitions attached, no agent framework. Capped at 1024 output tokens and 11 turns.

  • Why not Opus or Fable: it narrates an already-computed number. That does not need frontier reasoning, and paying for it would be spending on the one step where a wrong answer is impossible anyway, because the figure came from Go.
  • Why not Haiku: it does need to sequence several tool calls and hold a period's worth of figures straight while writing an owner-legible sentence.
  • Its non-test imports are exactly two packages: internal/llmclient and internal/mcptools. It has no path to internal/storage. Every number it sees arrived through a typed tool result.
A second, conditional call: a writer pass that rewrites the words, never the verdict. When the gate lands on ambiguous or unanswerable, a second model call — also Claude Sonnet 5, in the same internal/ambiguity package, and unaffected by the gate's model change — rewrites the clarifying question or refusal reason into clearer, more specific prose than the classification call is worth spending frontier-adjacent tokens on. It is structurally unable to overturn the gate's decision: its fixed reply schema (writerResponse) has no classification field at all, so there is nothing for the caller to read back even if the model tried. On an answerable question this second call never fires — cost stays exactly what it was. Both passes are logged as separate question_interaction rows, so the running cost total always reflects real calls made, never a single row standing in for two.

Both go through one shared client (internal/llmclient) with a 30-second bound on every call, so no model call anywhere in the system is untimed, uninstrumented, or unbounded. Pricing is held in one table there: $2/$10 per MTok for Sonnet 5 (the gate, its conditional writer pass, the explanation step, and spec 009’s opt-in business-insight advisor in internal/advisor — a per-tap call behind a deterministic Go trigger, ledgered in its own business_insight_interaction table), $1/$5 for Haiku 4.5 (the paraphrase-match cache check only, in internal/paraphrase) — and an unrecognised model id is an error, not a silent zero.

A third pathway, and the only one that produces something other than a fact. The Business Insight advisor (internal/advisor, internal/httpapi/business_insight.go, widened by specs/011-inline-grounded-advice) is split down the middle by the same line as everything else here, and the split is the point. It now has two ways in, both decided deterministically. The proactive way is unchanged from spec 009: whether an insight exists, and what it is about, is decided by deriveBusinessInsightTeaser — a plain Go function that runs on every answered question, over the tool results already in scope, at zero cost and with no model call. Most answers get nothing, which is the correct outcome, not a gap to fill with a generic tip. Only when the owner explicitly taps does the billed Claude Sonnet 5 call run behind POST /api/business-insight, and its trigger is re-verified in Go against the posted payload so no client can talk the advisor into advising on a pattern the data does not show. The question-initiated way (spec 011) fires when the owner explicitly asks for a suggestion — “how can I improve my margin overall?” — the ambiguity gate emits a typed advice-requested signal, the normal narration answers the data core first, and one advisor call then runs inline, grounded exclusively in the tool results that same answer computed; its prompt is assembled in plain Go from researched-practice sections selected by which tools actually ran, never chosen by the model, and an advice question nothing in the tool set can ground (“what should I pay my staff?”) is still refused plainly rather than answered generically. Two things keep both paths honest: the output is general industry practice connected to computed data — probabilistic advice, never a computed figure, which is why the diagram draws it dashed in the probabilistic purple rather than in the deterministic teal every number on this page uses; and every call, from either path, is logged to its own business_insight_interaction table (the inline path under kind question_advice), never question_interaction, so advisory spend can never be mistaken for the cost of answering a question.
A zero-cost fourth path: a meta-question never reaches either model. "What do you do?", "how can you help me?" used to reach the ambiguity gate, get correctly judged out-of-scope for the restaurant's data, and refused — honest, but the worst possible first impression. internal/httpapi/capability.go pattern-matches a fixed set of real meta-question phrasings before the cache probe or either model call, and answers directly from a hand-written, tool-grounded capability description — the same discipline as never asking a model to describe its own capabilities (it would happily invent one that doesn't exist). Zero tokens, zero latency, and gated on there being no clarification already in flight, so a bare reply like "hi" answering an unrelated clarifying question is never mistaken for a fresh meta-question.

This project's whole ambiguity/refusal discipline — classify cheaply first, refuse rather than fabricate, pair every non-answer with a concrete next step — is generalised into a reusable Claude Code skill, .claude/skills/question-recovery-design, so the same recovery-design pattern can be applied to a future chat or agent surface beyond this product. Its sibling, .claude/skills/proactive-guidance-design, covers the other half: what a chat surface should offer before the first question and after a successful one — the zero-state capability list and the follow-up suggestions above are its worked example in this exact codebase. The meta-question path above is question-recovery-design's newest worked example, folded into that skill's Move 5.

The answer cache

An exact-match lookup in Postgres, keyed on the question text normalised by trimming, collapsing internal whitespace and lowercasing. On a hit the previously-served response is returned verbatim — refusals and clarifications included, because a question that was unanswerable an hour ago is still unanswerable against the same data, and re-deciding it would cost two model calls to reach the same conclusion.

The disclosed limitation

“How did we do on 2026-08-07?” and “how was 2026-08-07” are different keys, and the second pays full price. Matching paraphrases needs a model call or an embedding lookup — either would put a probabilistic step in front of what is otherwise an O(1) index probe. A cache that decides two differently-worded questions mean the same thing can decide that wrongly, and serving the answer to a question nobody asked is a worse failure than paying for the second call.

A hit is the absence of a model call

So it is never written to question_interaction, which would fabricate an API call and inflate the running cost total with money nobody spent — and never left unrecorded, which would make real product activity invisible. It gets its own answer_cache_hit ledger carrying the cost it avoided. A saving, reported as a saving, never summed into spend. The response carries a separate cache field rather than a zero-cost entry, so no client can accidentally add the two together.

Invalidation is wholesale, and it happens first. Every ingestion run drops the entire cache before it writes anything. New source data can change any cached answer and there is no cheap way to know which; if the pipeline then fails partway, having already dropped the cache costs a few re-asked questions, whereas clearing only on success could leave answers cached against data that has already been partly rewritten. Correctness after new data beats retention, every time.

The chart-type decision

Which chart an answer gets is decided in plain Go, in internal/httpapi/visualization.go, from which typed tool actually ran and the shape of its deterministic result. It is never a second model call and never a field the narration model fills in. Asking a model “bar or pie?” would put the presentation of a financial figure back on the probabilistic side of the line for no benefit — the tool name already tells us the question's shape with certainty.

Follow-up suggestions: the same discipline applied to “what next”

Every answered question used to end in a blank composer — suggestion chips existed only in the empty state and inside a refusal, never after a success. internal/httpapi/suggestions.go's deriveFollowUpSuggestions closes that gap the identical way chart-type selection already works: a pure Go function keyed on which typed tool actually ran, parsing that tool's real arguments and result — never a second model call. Asking the model “what should the owner check next?” would be the same category error as asking it “bar or pie?”, with an added risk: a model-generated suggestion could name a question the product can't actually answer, which is the same class of lie as inventing a number.

Grounded, not generic

Every generated suggestion is built from the real date or period the answering tool was actually called with, clamped to the real min/max date range the product has data for — never a placeholder, never a date outside real coverage. Seven of the eight tools have at least one template — get_expense_pattern_by_day_of_month, the newest, has none yet, and a tool combination with nothing sensible to suggest returns an empty list, which is treated as a normal, honest outcome, not a bug to paper over.

One hop of conversation, not a transcript

A parallel mechanism, ambiguity.ComposeAnswerFollowUp, lets a bare reply like “and the day before?” resolve correctly — the same typed-pair discipline PendingClarification already applies to a clarification reply, extended to a real answer. Deliberately narrow: exactly the immediately preceding question and its answer text, never an accumulating history, per published research that longer, looser context is what causes a model to drift from what the user actually meant.

Hard limits & soft limits

Hard limits

  • Refuses rather than estimates when data is missing or incomplete. A confidently wrong margin figure is worse than a refusal.
  • No open SQL, no free-form computation. Eight defined, typed MCP tools, and nothing else.
  • 5-second timeout on every tool call and a hard 8-call cap per interaction, enforced in mcp-go's own dispatch middleware — not something an individual handler has to remember. Exceeding either returns a typed error the model can see and self-correct from, rather than crashing or truncating the interaction.
  • 30-second bound on every model call.
  • Chart selection is deterministic Go — never a second model call deciding how a financial figure is drawn.
  • Every number carries provenance: which file, which rows, which period. A refused answer carries none, rather than a fake one.
  • Every model call is logged with its real tokens, cost, latency, and whether the refusal or clarification path fired. A question that reaches the explanation step writes two rows, one per API call — merging them would mean dropping one call's cost.

Soft limits

  • The model is nudged toward the right framing, not hard-coded to one phrasing, so it can self-correct on rephrasings and unexpected question shapes.
  • Clarifying questions are asked rather than assumptions silently made — and any assumption that is taken is stated back.
  • A clarification reply travels as typed context, not as a pre-merged sentence, so question_interaction.question_text stays exactly what the user typed (“yes”) instead of recording a question they never asked.
  • One-tap clarification options are phrasings of a reply, never facts. Whichever is picked is posted back and re-classified from scratch, exactly as if it had been typed.

Where this would have to go — not built

What production would actually need

Listed as a destination, not as a disabled feature. None of it exists in this repository, and none of it is stubbed: there is no config flag that turns any of it on.

Data durability first. Managed Postgres with automated backups and point-in-time recovery, before anything else — the reconciled history is the product, and today a lost volume loses it. A read replica only becomes worth it once read load justifies the replication lag, which at one restaurant's data it does not.

Then the process. More than one backend instance behind a load balancer, with a real health endpoint and graceful shutdown. The backend is already stateless apart from the pool, so this is mostly deployment work rather than a rewrite — the answer cache and the interaction log already live in Postgres, not in memory.

Then ingestion. A scheduled, idempotent, resumable job with retries and a dead-letter path, instead of a CLI flag. Cache invalidation would move from “drop everything” to a scoped invalidation keyed on the dates the run actually touched — wholesale clearing is the right call at this size and the wrong one at any real volume.

Then everything a multi-tenant product needs and this prototype deliberately has none of: authentication, per-restaurant data isolation, rate limiting on /api/ask, a real CORS policy from configuration, and secrets from a secret manager rather than a shell profile.

And one thing that is genuinely not obvious: the per-interaction cost log already in question_interaction is the raw material for a spend budget per tenant. Getting that right is a product decision about what happens when an owner hits their cap — degrade to cached answers only, or refuse — and refusing is more in keeping with everything else here.

What was deliberately not built

No agent framework

Direct Anthropic API calls with the MCP tool definitions attached. The tool-calling loop is about forty lines of Go with an explicit turn cap, which is less code than configuring a framework and far easier to reason about when something goes wrong.

No multi-agent architecture

A handful of model calls with clearly different jobs — classify, write a refusal, narrate, match a paraphrase, advise on request — is not a multi-agent system, and calling it one would be dressing up a pipeline. Each is a single bounded call made by one Go function; there is no orchestrator, no agent-to-agent messaging, and nothing that would benefit from either.

No open-ended semantic search

A bounded exact-match cache with a Haiku-verified paraphrase layer now exists (internal/paraphrase) — it is not embeddings-based semantic search, on purpose: Anthropic has no first-party embeddings endpoint, and adding a second vendor for a cost optimization would reopen a single-vendor decision this constitution already made once. A false positive risk is real for any fuzzy match, so it is capped: 20 recent candidates, a verbatim-match requirement, and a live re-check before serving — a small, real, disclosed cost every time, never a free-seeming shortcut.

No open query tool

A “run this SQL” tool would answer more questions and would also let a model compute a number. That is the one thing this architecture exists to prevent, so it is not offered even as an internal convenience.

No point redemption

The Steward Points balance is real — a deterministic function of five badge codes now live (10 clean close, 25 caught discrepancy, 15 growth, 5 engagement, 30 campaign launcher). Spending them still needs an integration with promotional tooling this build has no access to, so redemption ships as a stated direction rather than a button that does nothing.

No cross-tenant support

One restaurant, one dataset, no auth, no account model — multi-tenancy (Segment 2) has a full spec and RFC (specs/005-multi-tenant/, docs/rfc-multi-tenant.md) but implementation is deliberately gated on human review: a tenant-isolation defect is a data-breach class of bug, not a UX one, and is not something to build under the same time pressure as everything else here.
